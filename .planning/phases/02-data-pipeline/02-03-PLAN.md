    1. Create src/lib/spotify/fetch-orchestrator.ts:

    A class SpotifyFetchOrchestrator that manages the entire data pipeline. Design per D-12 data flow: Spotify API (via proxy routes) -> raw tracks -> deduplicate -> collect artist IDs -> fetch artist genres -> send to worker.

    Constructor takes callbacks:
    ```typescript
    interface OrchestratorCallbacks {
      onProgress: (phase: string, loaded: number, total: number) => void
      onTrackBatch: (tracks: NormalizedTrack[], artistGenres: Record<string, string[]>) => void
      onComplete: () => void
      onError: (error: Error) => void
    }
    ```

    Rate limiting (Claude's discretion per CONTEXT.md):
    - Max concurrency: 2 parallel requests
    - Minimum spacing: 200ms between requests
    - On 429: pause ALL requests, wait for Retry-After seconds, then resume
    - Max retries per request: 3
    - Exponential backoff: 1s, 2s, 4s

    Deduplication (per Pitfall 6):
    - Maintain a Map<string, NormalizedTrack> keyed by Spotify track ID
    - When duplicate found: keep the entry with the "best" metadata. Priority: top ranking > saved (has addedAt) > playlist > recent
    - If existing has no topRanking but new one does, merge the ranking in

    Fetch order (per RESEARCH.md Fetch Order Strategy):
    1. Top tracks: 3 requests (one per time_range). Quick, provides ranking data for star sizing.
    2. Saved tracks: Paginated, 50 per page, up to offset 10000. This is the bulk.
    3. Recently played: 1 request, max 50 items. Small supplement.
    4. Playlists: Fetch playlist list, then each playlist's tracks. Most variable.
    5. Artists: Start fetching unique artist genres AS tracks accumulate (parallel with track fetching). Use the artist cache to avoid re-fetching.

    For each fetched batch of tracks from any source, normalize raw Spotify data into NormalizedTrack objects:
    - Extract track ID, name, primary artist name and ID from SpotifyTrackRaw
    - Set source field based on which endpoint the data came from
    - For top tracks: set topRanking with position and timeRange
    - For saved tracks: set addedAt from the saved track wrapper's added_at field
    - Deduplicate against existing tracks in the map

    Artist genre fetching:
    - Maintain Set<string> of artist IDs already fetched
    - As new artist IDs appear in track data, queue them for fetching
    - Fetch via GET /api/spotify/artists/[id] with rate limiting
    - Cache results in a Record<string, string[]> (artistId -> genres)

    The onTrackBatch callback fires periodically (e.g., every 50 tracks or when a source completes) with the current normalized tracks and artist genres. The consumer (useGalaxyPipeline) sends this to the Web Worker.

    The start() method begins the pipeline. An abort() method stops all pending fetches.

    On calling startPipeline():
    a. Create Worker instance using `new Worker(new URL("@/workers/galaxy-layout.worker.ts", import.meta.url), { type: "module" })`
    b. Wrap with Comlink.wrap<WorkerApi>(worker)
    c. Create SpotifyFetchOrchestrator with callbacks:

    useEffect cleanup: call orchestrator.abort() and worker.terminate() on unmount.

    Store interactions use getState() (not hooks) inside callbacks to avoid stale closures and unnecessary re-renders per Zustand best practices.
